## Summary

Connect support agent harnesses to the Zeeq telemetry endpoint to capture session-level information that can be incorporated into the dashboard and code review records.

Clients with native telemetry support:

- Codex / ChatGPT
- Claude Code / Claude
- VS Code Copilot

These can be pointed directly at the Zeeq telemetry endpoint via native configuration.

Other harnesses like OpenCode, Cursor, and Pi can use OpenTelemetry plugins or directly connect to the Zeeq ingest API endpoint.

![session-telemetry](/screens/session-telemetry.png)

Session telemetry captures:

- Conversation roots
- Session prompts and MCP tool usage (it does not capture local tool usage)
- Token usage and cost (calculated based on API rates)
- And option to produce PR level provenance linking to a session by linking the

## Configuring Codex

:::note
As of this writing, Codex can only be configured for OTEL via the root configuration at `~/.codex/config.toml`. See OpenAI [Advanced Config](https://learn.chatgpt.com/docs/config-file/config-advanced) and [Config Reference](https://learn.chatgpt.com/docs/config-file/config-reference) for details.
:::

:::tip
Your local client configuration can use the same access token for MCP and for telemetry; no need to create two.  You can name the token anything you like locally.
:::

Point your Codex client OTEL configuration to the Zeeq OTEL endpoint.

```md [~/.codex/config.toml]
[otel]
environment = "dev"
trace_exporter = "none"
log_user_prompt = true

[otel.exporter."otlp-http"]
endpoint = "https://otel.zeeq.ai/v1/logs"
protocol = "binary"

# Codex currently requires the OTLP Authorization header to be encoded directly;
# substitution will not work correctly.
# Mint this token: https://app.zeeq.ai/web/settings/credentials
[otel.exporter."otlp-http".headers]
authorization = "Bearer <ZEEQ_ACCESS_TOKEN_HERE>"
```

If `log_user_prompt` is set to `true`, the client will log the user prompt and the model response to the OTEL endpoint.

Codex responds with the conversation ID reliably when prompted:

```text
Print your current conversation/session ID.
```

Or more precisely:

```bash [Terminal]
printenv CODEX_THREAD_ID

# Or...
env | rg '^CODEX_THREAD_ID='
```

## Configuring Claude

Claude Code ignores repository `.claude/settings.json` and `.claude/settings.local.json` values for telemetry enablement and OpenTelemetry exporter variables. A project settings file can still select `otelHeadersHelper`, which Claude Code runs to obtain fresh request headers. Enable telemetry in the shell or user `~/.claude/settings.json`, or ask an administrator to set managed settings. See Anthropic's [administrator configuration](https://code.claude.com/docs/en/monitoring-usage#administrator-configuration) and [dynamic headers](https://code.claude.com/docs/en/monitoring-usage#dynamic-headers) documentation.

Claude Code's MCP OAuth login does not set `ZEEQ_OTEL_ACCESS_TOKEN`. Telemetry needs a Zeeq API token in the environment when Claude Code starts. You may use the same token for MCP and telemetry if it is a valid Zeeq API token, but OAuth login alone is not enough. Create a token at <https://app.zeeq.ai/web/settings/credentials> and keep it out of source control.

### Trusted central configuration

Trusted central configuration is supported. Administrators can set telemetry variables in the `env` block of managed settings. Individual developers can use the `env` block in `~/.claude/settings.json`. These trusted settings can enable telemetry and select its destination; repository settings cannot. Central settings apply across projects, while the launch options below scope telemetry to the Claude process started for a selected project. Managed settings can lock the collector destination.

For example, put non-secret exporter settings in `~/.claude/settings.json` and point `otelHeadersHelper` to an installed helper by absolute path. The helper still reads `ZEEQ_OTEL_ACCESS_TOKEN` from Claude Code's launch environment:

```json [~/.claude/settings.json]
{
  "otelHeadersHelper": "/Users/you/.local/bin/zeeq-otel-headers.sh",
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "https://otel.zeeq.ai",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_METRICS_EXPORTER": "none",
    "OTEL_LOG_USER_PROMPTS": "0",
    "OTEL_LOG_TOOL_DETAILS": "0"
  }
}
```

### Configure a project header helper

No version manager or environment loader is required. First add the helper entry alongside existing project settings in `.claude/settings.json`. The helper reads the token at launch time and fails clearly if it is missing:

```json [.claude/settings.json]
{
  "otelHeadersHelper": ".claude/zeeq-otel-headers.sh"
}
```

```bash [.claude/zeeq-otel-headers.sh]
#!/usr/bin/env bash
set -euo pipefail
: "${ZEEQ_OTEL_ACCESS_TOKEN:?Set ZEEQ_OTEL_ACCESS_TOKEN before launching Claude Code}"
printf '{"Authorization":"Bearer %s"}\n' "$ZEEQ_OTEL_ACCESS_TOKEN"
```

Make the helper executable before starting Claude Code:

```bash [Terminal]
chmod +x .claude/zeeq-otel-headers.sh
```

### Choose a launch method

Store `ZEEQ_OTEL_ACCESS_TOKEN` in a private shell secret store or ignored local file and export it in the environment that launches Claude Code. Do not commit it to the repository or put it in shared settings. Claude Code reads telemetry settings at process start, so restart existing sessions after changing them.

Each option below sets the same production OTLP configuration. Content capture stays off by default. Set `OTEL_LOG_USER_PROMPTS=1` and `OTEL_LOG_TOOL_DETAILS=1` only when you intend to collect prompt and tool content. These settings can include sensitive data. Zeeq derives token and cost metrics from log events, so the examples disable the separate metrics exporter. Claude Code appends `/v1/logs` to the base endpoint.

::code-group

```bash [Plain shell]
: "${ZEEQ_OTEL_ACCESS_TOKEN:?Set this in your private shell environment}"
(
  export CLAUDE_CODE_ENABLE_TELEMETRY=1
  export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
  export OTEL_EXPORTER_OTLP_ENDPOINT=https://otel.zeeq.ai
  export OTEL_LOGS_EXPORTER=otlp
  export OTEL_METRICS_EXPORTER=none
  export OTEL_LOG_USER_PROMPTS=0
  export OTEL_LOG_TOOL_DETAILS=0
  claude
)
```

```bash [Shell wrapper]
#!/usr/bin/env bash
set -euo pipefail
: "${ZEEQ_OTEL_ACCESS_TOKEN:?Set this in your private shell environment}"
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT=https://otel.zeeq.ai
export OTEL_LOGS_EXPORTER=otlp
export OTEL_METRICS_EXPORTER=none
export OTEL_LOG_USER_PROMPTS=0
export OTEL_LOG_TOOL_DETAILS=0
exec claude "$@"
```

```bash [Optional direnv]
# .envrc: ZEEQ_OTEL_ACCESS_TOKEN must already be set in the parent shell.
: "${ZEEQ_OTEL_ACCESS_TOKEN:?Set this in your private shell environment}"
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT=https://otel.zeeq.ai
export OTEL_LOGS_EXPORTER=otlp
export OTEL_METRICS_EXPORTER=none
export OTEL_LOG_USER_PROMPTS=0
export OTEL_LOG_TOOL_DETAILS=0
```

```toml [Optional mise]
[env]
CLAUDE_CODE_ENABLE_TELEMETRY = "{% if env.ZEEQ_OTEL_ACCESS_TOKEN is defined and env.ZEEQ_OTEL_ACCESS_TOKEN != '' %}1{% else %}0{% endif %}"
OTEL_EXPORTER_OTLP_PROTOCOL = "http/protobuf"
OTEL_EXPORTER_OTLP_ENDPOINT = "https://otel.zeeq.ai"
OTEL_LOGS_EXPORTER = "otlp"
OTEL_METRICS_EXPORTER = "none"
OTEL_LOG_USER_PROMPTS = "0"
OTEL_LOG_TOOL_DETAILS = "0"
```

::

Choose one method:

- **Plain shell:** Run the commands in a terminal that has the exported token. The subshell keeps the exporter settings separate from unrelated commands.
- **Wrapper:** Save the script as `scripts/claude-with-telemetry`, make it executable with `chmod +x scripts/claude-with-telemetry`, then run it from the project root. The script forwards arguments to Claude Code. If you use [asdf](https://asdf-vm.com/guide/getting-started.html), complete its shell setup first so its shims are on `PATH`. The wrapper runs the `claude` command resolved by that shell; it does not install Claude or configure asdf. asdf selects tool versions; the wrapper supplies the telemetry variables.
- **[direnv](https://direnv.net/):** Save the example as `.envrc`, review it, then run `direnv allow`. Launch with `direnv exec . claude`. A [shell hook](https://direnv.net/docs/hook.html) is optional for this explicit launch command. A shell hook instead loads the variables automatically when you enter the directory.
- **[mise](https://mise.jdx.dev/environments/):** Save the TOML as `mise.toml`, review and trust the configuration, then launch with `mise exec -- claude`. mise is optional.

Other launch-time environment loaders include [dotenvx](https://dotenvx.com/docs/quickstart) and [env-cmd](https://github.com/toddbluhm/env-cmd). Follow their documentation to supply the same variables. Keep the token in a private source. Never put its value in a shared `.envrc`, `mise.toml`, or environment file.

### Verify and troubleshoot

Send a prompt and an MCP tool call, then check the Zeeq Sessions inbox and telemetry metrics. A processed session can still take time to appear in dashboard metrics. Claude Code may also create auxiliary events such as `generate_session_title`; Zeeq counts reported completion usage and cost once, including auxiliary events, but hides a session from the inbox until persisted history includes a non-housekeeping prompt, tool result, or completion. The existing minimum-cost filter still applies. Later real work makes an earlier auxiliary-only session visible.

If Claude Code reports `otelHeadersHelper failed` in `/status` or its debug log, check that the helper is executable and that `ZEEQ_OTEL_ACCESS_TOKEN` is present in the environment that launched Claude Code. A collector `401` usually means the token is missing, invalid, expired, or issued by the wrong Zeeq environment. A production token is not valid for the local issuer. Do not bypass local authentication; create a token from the local environment.

Claude Code can respond with the conversation ID when prompted for:

```text
Get your conversation ID from the current active scratchpad path.
```

## Direct import (Pi, Cursor, OpenCode, etc.)

Several harnesses do not have native OTEL support and must use either plugins that emulate OTEL or write a custom hook.

- [Cursor](https://github.com/LangGuard-AI/cursor-otel-hook)
- [OpenCode](https://github.com/DEVtheOPS/opencode-plugin-otel)

If preferred, for these harnesses, it is possible to use the Zeeq telemetry import API directly and send a JSON payload.

### Pi

Zeeq publishes a first-party Pi extension that posts session telemetry directly to the Zeeq import API so no OTEL config or hook script required.  You can check the source of the hook to write a custom extension for other harnesses.

::steps{level="4"}

#### Install the extension

The extension is published to npm as [`@zeeq-ai/zeeq-app-pi-telemetry`](https://www.npmjs.com/package/@zeeq-ai/zeeq-app-pi-telemetry). Run this from the root of the repository you want to emit telemetry from:

```bash [Terminal]
pi install --local npm:@zeeq-ai/zeeq-app-pi-telemetry
```

To track patch releases automatically while holding the minor version, pin a tilde range instead:

```bash [Terminal]
pi install --local "npm:@zeeq-ai/zeeq-app-pi-telemetry@~1.0.1"
```

Pi writes the package source to `.pi/settings.json`. Approve the project-local package so Pi trusts and loads it:

```bash [Terminal]
pi --approve
```

#### Create an access token if using DCR

Visit <https://app.zeeq.ai/web/settings/credentials> and create a new API token if you are using dynamic client registration (DCR) for your authentication.

Store it in your shell profile (`.zshrc`, `.bashrc`, `$PROFILE`, etc.) as `ZEEQ_ACCESS_TOKEN`:

```bash [Terminal]
export ZEEQ_ACCESS_TOKEN="<token>"
```

:::tip
If you are already using token based auth, you can use the same token you are using for authenticating.
:::

:::note
Don't forget to refresh your shell environment so the token is available to the Pi process: `source ~/.zshrc` or `source ~/.bashrc`
:::

#### Start a session

No further configuration is required — the extension sends telemetry to Zeeq's hosted endpoint by default as soon as `ZEEQ_ACCESS_TOKEN` is set. Start Pi as normal in the trusted project and telemetry uploads automatically in the background.

#### Configure prompt text privacy

By default, the Pi extension exports prompt text. To omit prompt text while keeping prompt length metadata, set:

```bash [Terminal]
export ZEEQ_OTEL_OMIT_PROMPT="1"
```

When enabled, `prompt_text` is exported as `omit_by_config`.

To keep only a prefix of each prompt, set:

```bash [Terminal]
export ZEEQ_OTEL_TRUNCATE_PROMPT="32"
```

Truncated prompt text is exported as the retained prefix followed by `...(truncated_by_config)`. A value of `0`, an empty value, or an omitted variable disables config truncation. Positive values below `16` are treated as `16`.

#### Troubleshooting

Confirm the extension is installed and trusted:

```bash [Terminal]
pi list
```

Enable export error logging so failed uploads print to stderr instead of failing silently:

```bash [Terminal]
export PI_TELEMETRY_LOG_ERRORS="true"
```

Force an immediate upload instead of waiting for the batch timer, using the extension's own command from inside a Pi session:

```text
/telemetry-flush
```

:::note
A `401` on export almost always means `ZEEQ_ACCESS_TOKEN` is missing, expired, or shadowed by another token exported earlier in your shell profile (later `export`s win). Re-mint a token at <https://app.zeeq.ai/web/settings/credentials> if unsure.
:::

::

### Raw API shape

The API endpoint for this is available at `https://app.zeeq.ai/api/v1/telemetry/import` and requires an `Authorization: Bearer <token>` header with a valid Zeeq API token.

The payload shape:

::code-collapse

```json [POST /api/v1/telemetry/import]
{
  "conversation_id": "conv_local-session-abc123",
  "harness_name": "my-harness",
  "harness_version": "1.4.0",
  "repository_remote_url": "https://github.com/my-org/my-repo",
  "head_branch": "main",
  "head_sha": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2",
  "events": [
    {
      "kind": "Prompt",
      "event.timestamp": "2026-07-24T14:35:07.281Z",
      "prompt_text": "Tell me a joke",
      "prompt_length": 15,
      "gen_ai.request.model": "gpt-5.5"
    },
    {
      "kind": "ToolResult",
      "event.timestamp": "2026-07-24T14:35:08.512Z",
      "gen_ai.tool.name": "bash",
      "gen_ai.tool.call.id": "call_1",
      "gen_ai.tool.call.arguments": { "command": "ls" },
      "gen_ai.tool.call.result": "README.md\nsrc/",
      "gen_ai.tool.call.duration_ms": 42,
      "gen_ai.tool.call.success": true
    },
    {
      "kind": "Completion",
      "event.timestamp": "2026-07-24T14:35:10.208Z",
      "gen_ai.request.model": "gpt-5.5",
      "gen_ai.usage.input_tokens": 4267,
      "gen_ai.usage.cached_tokens": 0,
      "gen_ai.usage.output_tokens": 66,
      "gen_ai.usage.reasoning_tokens": 0,
      "zeeq.cost.usd": 0.023315
    }
  ]
}
```

::

- `conversation_id` and `harness_name` are required at the top level; `events` must contain at least one entry.
- `harness_version`, `repository_remote_url`, `head_branch`, and `head_sha` are optional but power PR-level provenance linking — send them when available.
- Each event's `kind` is one of `Prompt`, `ToolResult`, or `Completion`. Send `Prompt` for user input, `ToolResult` per tool call, and `Completion` once per model response with token counts.
- `zeeq.cost.usd` is optional. When your client can report a provider-normalized cost, send it and Zeeq treats it as authoritative; otherwise Zeeq estimates cost from token counts.

:::note
Any `user.email` or `organization_id` field sent on an event is ignored — Zeeq always attributes the request to the identity behind your bearer token.
:::
