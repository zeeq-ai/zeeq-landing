## Summary

Knowledge libraries hold *canonical* guidance, but agents are often the first to notice that a document is wrong, stale, or missing. Agent-authored documents let a coding agent fix a document or add a new one from inside the same session, so the knowledge base improves as the work happens instead of after it.

Because these libraries are canonical, the feature is built around guardrails:

- **The developer approves first.** The agent shows the diff or the draft in the session and waits for approval before it writes.
- **Edits apply only to the version the agent read.** If the document changed in the meantime, nothing is saved and the agent rebuilds its edit.
- **Source-owned documents are never edited in Zeeq.** Documents synced from GitHub or Notion are edited at their source.
- **Every change is audited** with a snapshot, the rationale, and who made it.

::note
The `create_document` and `update_document_by_diff` MCP tools are available to any member of the organization for libraries they can access.
::

Nothing special has to be added to your skills or `AGENTS.md`. The tool descriptions guide the agent through the flow, including matching the tone, voice, and style of the existing documents.

## Document ownership

Every document has an owner, and the owner decides who can change it:

| Owner | Where it comes from | Agents can edit it |
|--|--|--|
| **Manual** | Authored directly in Zeeq | Yes |
| **Agent** | Created by an agent with `create_document` | Yes |
| **Synced** | Ingested from GitHub or Notion | No; edit at the source |

When an agent reads a document, the result ends with a metadata block containing the library, path, `contentHash`, source, whether it is editable, and links back to the source when there is one. The `contentHash` identifies the exact version the agent is working from.

## Creating documents

An agent creates a document with a library, a path, the Markdown content, and a short rationale. The document is live as soon as it is saved and is marked as Agent-owned.

Creation never overwrites. If a document already exists at the path, the response describes it (title, hash, owner, source links) and the agent either reads it or picks a more specific path.

## Updating documents

The agent follows this flow:

1. Read the document and keep its `contentHash`.
2. Make the smallest change that meets the request, matching the document's style.
3. Produce a one-file unified diff with at least three unchanged lines of context around each change (fewer only at the start or end of the file), with hunks in document order.
4. Show the diff to the developer and wait for approval.
5. Call `update_document_by_diff` with the hash, the diff, and a rationale. The response returns the new hash for any later edit.

Zeeq applies the diff only if the stored document still matches the hash. It then checks that every hunk matches exactly one place, that the result is not empty, and that it is within the size limits.

### When an edit isn't applied

Nothing is saved in any of these cases. The response is flagged as an error (`isError`) so clients and agents can tell the call failed, and it tells the agent what to do next:

- **Stale.** The document changed after it was read. The response includes the current content and hash so the agent can rebuild the edit, show the revised diff, and try again.
- **Rejected.** The diff was malformed, didn't match, matched more than one place, or would empty the document. The response names the reason and the fix. An invalid path or input is rejected as `invalid_input`.
- **Not editable.** The document is synced from GitHub or Notion. The response includes the source link so the change can be made there.

::tip
If a write ever returns `saved: unknown`, the agent reads the document before trying again to check whether the change landed.
::

### Limits

| Item | Limit |
|--|--|
| Rationale | 2,000 characters, required |
| New document content | 200,000 characters |
| Diff, and the document it applies to | 1,000,000 characters |
| Saved result of an edit | 200,000 characters |

Limits count UTF-16 code units. Documents that mix LF and CRLF line endings are rejected; normalize the line endings first.

## Sync and recovery

Repository and Notion sync only update and remove **Synced** documents. If a synced source collides with a path owned by a Manual or Agent document, the sync skips that path, logs it, and the local document stays. An Agent document therefore remains in the library across later sync runs.

Each create or content-changing update records an audit snapshot, the rationale, the authenticated actor, and the MCP client name when available. The snapshot lets a person compare and restore the earlier content by re-saving it. There is no automated revert. Updating an Agent document through the UI or HTTP adopts it as Manual.

## Source links

For synced documents, Zeeq links back to where the change should be made:

- **GitHub**: links point to `HEAD` using the original source path when it is available. Older records and public-source documents may only have a normalized path, so check the filename if a link doesn't open. Links are generated for HTTPS `github.com` repositories; GitHub Enterprise links are not supported.
- **Notion**: the page link is included when Zeeq has a valid page ID. There is no edit link for Notion.

For the exact tool descriptions and parameters the agents see, read the [MCP Tools Inventory](/docs/architecture/tools-inventory).
